**# Milestone v0.0.8 — Observation Foundation**

**## Status**

🚧 **\*\*In Progress\*\***

\> The reusable Observation Foundation is architecturally established.

\> The overall v0.0.8 milestone remains in progress while the first

\> concrete Observation Provider is implemented and verified.

**---**

**# Goal**

Establish a modular Observation Foundation that allows AegisFlow to observe meaningful developer workspace activity through independent provider plugins.

The foundation defines the common architecture that future providers such as Git, Terminal, and Filesystem will follow.

The Observation Foundation is designed to separate:

\- Observation modeling

\- Provider management

\- Provider discovery

\- Provider validation

\- Configuration

\- Observation transport

\- Provider lifecycle

\- Provider-specific implementation

The reusable foundation is complete enough to begin implementation of the first concrete provider.

**---**

**# Architectural Goal**

The Observation Foundation introduces a provider-oriented architecture:

\`\`\`text

Developer Workspace

        │

        ▼

Observation Providers

        │

        ▼

Observation

        │

        ▼

Observation Publisher

        │

        ▼

Observation Bus

        │

        ▼

Future Consumers

\`\`\`

Providers remain independently modularized and do not need to know how observations are consumed.

**# 1. Observation Core**

The Observation Core defines the common domain concepts shared by all providers.

\`\`\`text

core/

├── observation.py

├── metadata.py

├── enums.py

├── exceptions.py

└── provider.py

\`\`\`

**## Responsibilities**

\- Define the canonical \`Observation\` model.

\- Define shared observation metadata.

\- Define common enums.

\- Define Observation-specific exceptions.

\- Define the \`ObservationProvider\` contract.

**---**

**# Observation Model**

Every provider produces a complete \`Observation\` object.

Conceptually:

\`\`\`text

Observation

id

provider

observation\_type

occurred\_at

metadata

\`\`\`

The \`Observation\` is the canonical object passed through the Observation Foundation.

Providers must not send raw dictionaries as the internal Observation contract.

The same complete \`Observation\` object moves through the system:

\`\`\`text

Provider

    │

    ▼

Observation

    │

    ▼

Publisher

    │

    ▼

Bus

    │

    ▼

Subscriber

\`\`\`

**---**

**# Provider Contract**

Every provider follows the same lifecycle:

\`\`\`text

initialize()

    │

    ▼

start()

    │

    ▼

observe()

    │

    ▼

Observation objects

    │

    ▼

stop()

\`\`\`

**## \`initialize()\`**

Prepares resources required by the provider.

It should not begin continuous observation.

**## \`start()\`**

Activates the provider and prepares it to produce observations.

**## \`observe()\`**

Produces observations as an asynchronous stream.

Every yielded item must be a complete \`Observation\` object.

**## \`stop()\`**

Stops observation and releases provider resources.

The provider is responsible for observing its external system.

The provider is not responsible for interpreting observations or generating business events.

**---**

**# 2. Provider Registry**

The Registry manages available Observation Providers.

\`\`\`text

registry/

├── registry.py

├── discovery.py

└── validator.py

\`\`\`

**## Responsibilities**

\- Register providers.

\- Unregister providers.

\- Retrieve providers.

\- Discover providers.

\- Validate provider implementations.

The Registry answers:

\> **\*\*What providers are available?\*\***

It does not decide which providers should run.

**---**

**# Provider Discovery**

Provider discovery provides the mechanism for identifying available provider implementations.

Discovery remains separate from registration so that future discovery mechanisms can be introduced without changing the Registry's core responsibility.

**---**

**# Provider Validation**

Provider validation ensures that discovered or registered providers satisfy the common \`ObservationProvider\` contract.

Invalid providers must not become part of the active provider set.

**---**

**# 3. Observation Configuration**

Configuration defines which providers should participate in the Observation runtime.

\`\`\`text

config/

├── settings.py

└── loader.py

\`\`\`

Configuration answers:

\> **\*\*Which providers should be enabled?\*\***

The current configuration foundation provides:

\`\`\`text

enabled

providers

environment

\`\`\`

Provider-specific configuration is intentionally outside the foundation and belongs to the individual provider implementation.

For example, Git-specific settings should eventually remain inside the Git Provider rather than inside the global Observation configuration.

**---**

**# Configuration Responsibility**

The separation is:

\`\`\`text

Registry

    │

    └── What providers are available?

Configuration

    │

    └── What providers are enabled?

Loader

    │

    └── Which enabled providers can be loaded?

\`\`\`

This prevents configuration and provider discovery from becoming tightly coupled.

**---**

**# 4. Observation Bus**

The Observation Bus provides in-process communication between providers and consumers.

\`\`\`text

bus/

├── bus.py

├── publisher.py

└── subscriber.py

\`\`\`

Architecture:

\`\`\`text

Provider

   │

   ▼

Observation Publisher

   │

   ▼

Observation Bus

   │

   ├──► Subscriber

   ├──► Subscriber

   └──► Subscriber

\`\`\`

**## Publisher**

The Publisher provides the interface used by providers or provider-side components to publish complete \`Observation\` objects.

Conceptually:

\`\`\`text

Provider

    │

    ▼

ObservationPublisher

    │

    ▼

ObservationBus

\`\`\`

Providers do not need to know how the internal Bus manages subscribers.

**## Bus**

The Bus delivers observations to registered subscribers.

The initial implementation is intentionally:

\- In-process

\- Asynchronous

\- Simple

\- Provider-independent

The Bus does not introduce a distributed message broker.

**## Subscriber**

The Subscriber defines the contract for components that consume observations.

Subscribers receive:

\`\`\`text

Observation

\`\`\`

not:

\`\`\`text

dict

\`\`\`

The complete \`Observation\` object remains the internal communication contract.

**---**

**# Observation Bus Responsibilities**

The Bus is responsible for:

\- Registering subscribers.

\- Removing subscribers.

\- Delivering observations.

\- Preserving the \`Observation\` object.

The Bus is not responsible for:

\- Observing developer activity.

\- Interpreting observations.

\- Converting observations into business events.

\- Persisting observations.

\- Discovering providers.

\- Managing provider-specific logic.

**---**

**# Observation Transport Boundary**

The Observation Bus establishes this boundary:

**# 5. Provider Lifecycle Foundation**

The Lifecycle subsystem manages provider execution without containing provider-specific logic.

Current structure:

\`\`\`text

lifecycle/

├── health.py

├── loader.py

├── starter.py

└── stopper.py

\`\`\`

The Runtime coordinator is intentionally not implemented yet.

**---**

**# Provider Health**

\`health.py\` tracks provider runtime state.

Supported states:

\`\`\`text

CREATED

INITIALIZING

READY

RUNNING

STOPPING

STOPPED

FAILED

\`\`\`

The Health Tracker only records provider state.

It does not:

\- Start providers.

\- Stop providers.

\- Restart providers.

\- Observe provider activity.

\- Publish observations.

**---**

**# Provider Loader**

\`loader.py\` combines Configuration and Registry.

\`\`\`text

Configuration

      │

      │ enabled providers

      ▼

    Loader

      │

      │ available providers

      ▼

   Registry

      │

      ▼

Loaded Provider Instances

\`\`\`

The Loader:

\- Checks whether Observation is enabled.

\- Reads configured provider types.

\- Retrieves providers from the Registry.

\- Returns loaded provider instances.

The Loader does not initialize or start providers.

**---**

**# Provider Starter**

\`starter.py\` manages provider startup.

Startup follows:

\`\`\`text

Provider

    │

    ▼

INITIALIZING

    │

    ▼

initialize()

    │

    ▼

READY

    │

    ▼

start()

    │

    ▼

RUNNING

\`\`\`

If startup fails:

\`\`\`text

Provider

    │

    ▼

FAILED

\`\`\`

Providers are started independently.

A failure in one provider does not automatically prevent unrelated providers from starting.

The Starter does not call \`observe()\`.

Continuous observation will eventually be coordinated by the Runtime.

**---**

**# Provider Stopper**

\`stopper.py\` manages provider shutdown.

Shutdown follows:

\`\`\`text

RUNNING

    │

    ▼

STOPPING

    │

    ▼

stop()

    │

    ▼

STOPPED

\`\`\`

If shutdown fails:

\`\`\`text

RUNNING

    │

    ▼

STOPPING

    │

    ▼

FAILED

\`\`\`

Providers are stopped independently.

A failure in one provider does not automatically prevent unrelated providers from releasing their resources.

**---**

**# Provider Independence**

Providers are independently managed.

For example:

\`\`\`text

Git          → RUNNING

Terminal     → FAILED

Filesystem   → RUNNING

\`\`\`

A failure in one provider must not automatically stop unrelated providers.

Automatic retry and recovery policies are outside the current scope.

**# Current Provider Milestone**

The first concrete Observation Provider has been implemented:

**## Git Provider**

The Git Provider is the reference implementation for the provider architecture.

It follows:

```text
ObservationProvider

        │

        ├── initialize()

        ├── start()

        ├── observe()

        └── stop()
```

The implemented Git Provider observes:

```text
repository.detected
branch.changed
working_tree.changed
commit.changed
```

The provider also maintains Git state containing:

```text
branch
working_tree_clean
commit
commit_message
```

The Git Provider is responsible only for local Git observation.

It does not interpret observations or generate business events.

---

**# Git Provider Verification**

The Git Provider has been verified through provider tests and an end-to-end lifecycle test.

Verified behavior:

- No observation before `start()`.
- Git repository detection.
- One-time `repository.detected`.
- Duplicate repository detection suppression.
- Branch transition detection.
- Dirty working-tree detection.
- Clean working-tree detection after a commit.
- Local commit change detection.
- Commit SHA and commit message metadata.
- No observations after `stop()`.

The verified lifecycle is:

```text
Repository detected
        │
        ▼
repository.detected
        │
        ▼
Branch changes
        │
        ▼
branch.changed
        │
        ▼
Working tree becomes dirty
        │
        ▼
working_tree.changed
        │
        ▼
Commit created
        │
        ├──────────────► working_tree.changed
        │                working_tree_clean = True
        │
        ▼
commit.changed
        │
        ▼
Provider stopped
```

**# Design Principles**

\- Build incrementally.

\- Complete one architectural responsibility before moving to the next.

\- Keep every provider independently modular.

\- Do not create a centralized provider-specific manager.

\- Keep provider-specific logic inside the provider.

\- Use complete \`Observation\` objects as the internal contract.

\- Never use raw dictionaries as the canonical Observation transport object.

\- Keep Observation transport separate from Observation interpretation.

\- Keep provider lifecycle separate from provider implementation.

\- Keep configuration separate from provider discovery.

\- Keep Registry responsible for available providers.

\- Keep Loader responsible for selecting configured providers.

\- Keep Starter responsible for provider startup.

\- Keep Stopper responsible for provider shutdown.

\- Keep Health responsible for provider runtime state.

\- Prefer simple in-process infrastructure before introducing distributed systems.

\- Do not build future infrastructure until the current layer requires it.

\- One provider failure must not automatically stop unrelated providers.
